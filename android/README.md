# LaTeX Squiggly for Android

**A draft.** Nothing here has been run on a phone yet. The engine passes the
same conformance checks as every other platform, the renderer page passes its
tests in Chromium, and the app code type-checks against Android's own classes.
Everything that needs a phone is untested: see [What is untested](#what-is-untested).

Android doesn't let an app watch what you type in other apps, which is how the
desktop apps work. So on Android, LaTeX Squiggly offers three things that work
within Android's rules:

| | What it does | Works with |
|---|---|---|
| **The maths keyboard** | Type `\alpha`, press space, get α. The strip above the keys shows what space will do before you press it. **Render** turns the LaTeX before the cursor into an image and inserts it. | Any app, once you switch to the keyboard |
| **Convert LaTeX** | Select LaTeX in any app and choose *Convert LaTeX* from the selection menu. The selection is replaced with the characters. | Any keyboard |
| **Render LaTeX** | Select LaTeX and choose *Render LaTeX*, or open the renderer from the app. The result is an image to copy, insert or save. | Any keyboard |

The keyboard isn't meant to replace your usual one. It has no autocorrect,
swipe typing or voice input, and it doesn't try to. You switch to it when you
need maths, and the 🌐 key takes you straight back. Holding 🌐 opens the
system's keyboard picker.

## Building

```
android/gradlew -p android :app:assembleDebug     # needs the Android SDK
android/gradlew -p android :engine:conformance    # needs only Java
```

The debug APK is at `android/app/build/outputs/apk/debug/`. CI builds it on
every push, and the build can be downloaded from the run's *Artifacts* section
as `latex-squiggly-android-debug`.

The app needs Android 9 (API 28) or later and targets API 36.

## How it is put together

```
android/
  engine/                  plain Kotlin with no Android in it, checked on any JVM
    Engine.kt              the converter and the trigger rules, ported from chrome/engine/engine.js
    Tables.g.kt            generated by scripts/generate-kotlin-tables.py
    Selection.kt           rules for the selection menu, which only Android has
    src/conformance/       replays conformance/reference.json, plus the selection checks
  app/
    keyboard/              the input method: KeyboardService, its view and its layouts
    selection/             Convert LaTeX
    render/                the renderer activity, its JavaScript bridge and the image provider
    web/files.json         the renderer page's files, copied from chrome/ at build time
    MainActivity.kt        setup, a box to try the keyboard in, and settings
```

**The engine is a fourth port, held to the same reference as the others.**
Its tables are generated from the Swift engine, and `:engine:conformance`
replays all 2,030 fragments and requires the same answer as the Swift engine,
down to the delete count. `scripts/check-all.sh` runs it.

**The renderer is the extension's own page**, as on the Mac. It runs in a
`WebView`, served from the app's assets at `https://appassets.androidplatform.net/`
because a WebView will not load ES modules from `file://`. Every other address
is refused. `chrome/renderer/host.js` has a third host for Android, which talks
to `RendererBridge.kt`. `chrome/test/android-window.cjs` runs the page in
Chromium against a stand-in for the bridge.

**No libraries, no permissions.** The app uses only the platform: no AndroidX,
no Compose, no support library. The manifest asks for no permissions at all,
not even `INTERNET`. A keyboard sees everything typed into it, and Android
warns about that when you turn one on. The strongest answer is one the system
enforces: this app cannot reach the network.

## Behaviour that differs from the desktop apps

- **The keyboard reads the text before the cursor rather than keeping a
  buffer of keystrokes.** A keyboard can ask the text box directly, so each
  replacement is checked against the actual text it replaces before anything
  is deleted. It reads up to 64 characters, the same amount the desktop apps
  keep.
- **Backspace straight after a conversion puts the LaTeX back**, the way
  undoing an autocorrection works. The next space then leaves that LaTeX alone.
- **It never converts in password fields, or in the renderer's own text box**,
  which needs the LaTeX exactly as typed.
- **There is no list of excluded apps.** You switch to the keyboard when you
  want maths, so that choice is the exclusion. For the same reason the setting
  to stop converting on space is a single switch.
- **Return never converts**, the same rule as every other platform.
- **Selections convert all or nothing.** If the selection is wrapped in `$...$`,
  `\(...\)` or similar delimiters, they are removed first. If it contains
  `$...$` spans inside ordinary text, each span is converted and the text
  around them is left alone. Anything else is converted as a whole.

## What is untested

Everything below needs a real phone or an emulator:

- The keyboard itself: layout and sizing on different screens, key repeat,
  shift, the symbol pages, haptics, and dark mode.
- Whether `getTextBeforeCursor` and `deleteSurroundingText` behave in
  WebView-based editors and the less standard text boxes, such as Google Docs,
  Slack and Discord. These are the usual trouble spots for third-party
  keyboards.
- Inserting images with `commitContent`. Apps that accept images through the
  keyboard (Messages, WhatsApp, Gmail and others) differ in whether they
  attach the image or send it straight away.
- Pasting an image from the clipboard. How well this works depends on the
  app you paste into.
- The selection menu entries. Where they appear varies by app and Android
  version, and some apps hide them under ⋮.
- The renderer's `WebView`: insets on Android 15's edge-to-edge layout, the
  soft keyboard covering the page, and the save dialog.

## Not done yet

- A *Share* button in the renderer. On a phone, sharing is often a more natural
  way to send an image than copying it.
- Popups that enlarge a key while it is pressed, and long-press for
  alternative characters.
- Release signing and a Play Store listing. New personal Play developer
  accounts must run a closed test with 12 testers for 14 days before
  publishing; check Google's current rules before planning a release.
